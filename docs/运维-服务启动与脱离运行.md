# 运维：服务启动与「脱离调用方」运行

## 事故（2026-09-15 19:34 实测）

启动器任务结束时，后端被**连带杀掉**，8000 端口拒绝连接、系统里没有 uvicorn 进程。

判定为外部终止、而非自身崩溃的证据：

- `.run\backend.log` 最后写入 **19:34:34**，内容仍是正常的健康输出
  （`GET /api/health/ready 200`、APScheduler `QuoteScheduler.poll_once` 每 3 秒 executed successfully）；
- `.run\backend.err.log` 末尾只有 19:32:45 的 `tdxpy NotImplementedError` 噪声，**没有崩溃回溯**；
- `.run` 下没有残留 pid 文件，端口直接拒绝连接 —— 典型「被作业对象整树回收」。

影响：15:30 结算调度随之停摆。当日结算已完成（前向观察 `2026-09-14-paper-costs-v2` = 1/60，
`last_counted_day=2026-09-15`），因此没有丢数据，但服务必须重新拉起。

## 根因（两条，都在 `scripts\start_all.ps1`）

1. **进程归属**：`Start-Process` 创建的子进程留在调用方的 Windows 作业对象里。调用方
   （自动化任务被回收、或用户关掉终端窗口）结束时，后端被一起杀掉。
   同类陷阱在项目自己的 `scripts\launcher.ps1:337` 已有注释记载（不依赖 Start-Process 的退出码）。
2. **退出码误报**：迁移直接写 `& $venvPython -m alembic upgrade head`，alembic 把 `INFO` 写到 stderr，
   Windows PowerShell 5.1 会把它包成 `NativeCommandError`，于是调用方看到的是
   **「明明启动成功却返回 exit 1」**——自动化无法用它判断成败。

## 修法（`scripts\start_all.ps1`）

1. 后端改为经 WMI 创建：
   `Invoke-CimMethod -ClassName Win32_Process -MethodName Create`，进程归 **WmiPrvSE** 所有，
   调用方退出后继续运行。
2. WMI 创建**不继承**本进程环境变量，因此按白名单显式透传脚本自己设过的那些：
   `SERVE_STATIC`、`HOST`、`DATABASE_URL`、`REQUIRE_AUTH`、`ACCESS_PASSWORD`、`SESSION_SECRET`、
   `PATH`、`PYTHONIOENCODING`、`LOG_LEVEL`（LAN 模式的口令变量因此不会丢）。
3. 迁移改为 `Start-Process -NoNewWindow -Wait -PassThru` 并把输出重定向到
   `.run\alembic.log` / `.run\alembic.err.log`，用 `.ExitCode` 判定成败。
4. 就绪判定改为检查包装进程是否还在（不再依赖 `.NET Process` 对象），失败时用
   `taskkill /T /F` 整树清理。
5. pid 文件约定：`.run\backend.pid` = **包装进程**（`cmd.exe`，`stop_all.ps1` 用 `taskkill /T`
   整树停止，仍然干净）；`.run\backend.python.pid` = 真正的 uvicorn python 进程，仅作查看用。
   python PID 在**就绪之后**才记录（创建包装进程的瞬间它还没起来，早查会得到空值）。

## 验证（实测输出）

| 检查项 | 结果 |
| --- | --- |
| `powershell -ExecutionPolicy Bypass -File scripts\start_all.ps1 -Prod` | 打印 `=== Launch OK (prod) ===`，**EXITCODE=0** |
| `GET http://127.0.0.1:8000/` | **200**，响应含 `index-*.js` —— 证明 `SERVE_STATIC` 经白名单透传成功（透传失败只会 404） |
| `GET /api/health` | `status=ok`、`scheduler.running=True`、`settlement_scheduler.running=True`、`database.ok=True` |
| pid 文件 | `backend.pid=249836`、`backend.python.pid=233224` |
| 调用方退出后存活（另起一次调用复核） | 249836 与 233224 **均存活**，健康检查仍 `ok` |
| 包装进程归属 | `ParentProcessId=5480` → `WmiPrvSE`（WMI 提供程序服务），不是调用的 shell |

## 日常用法

```powershell
# 启动（正式部署：后端托管 frontend\dist，只占 8000）
powershell -ExecutionPolicy Bypass -File scripts\start_all.ps1 -Prod

# 重启 / 停止
powershell -ExecutionPolicy Bypass -File scripts\restart_all.ps1 -Prod
powershell -ExecutionPolicy Bypass -File scripts\stop_all.ps1

# 只看是否还活着
Get-Content .run\backend.pid, .run\backend.python.pid
Invoke-WebRequest http://127.0.0.1:8000/api/health -UseBasicParsing
```

## 未改动的地方（明确保留）

- **dev 模式的前端 Vite**（`start_all.ps1:348`）仍是 `Start-Process`：dev 代理进程随调用方结束而结束
  是合理的，且 prod 模式根本不起 Vite。
- **`scripts\start_backend.ps1`** 是前台 `--reload` 开发脚本（阻塞式、给人看日志用），
  其中 alembic 仍是 `&` 直调；它不用于自动化，故未改。
- 曾临时新增过 `scripts\start_backend_detached.ps1` 用于抢修，其后已删除——
  `start_all.ps1 -Prod` 现在本身就是脱离式启动，保留两份实现只会漂移。
