## 1. 产品目标与非目标

### 1.1 最终目标

平台应在交易时段以可核验的真实行情持续更新，给出“当前策略体系下最值得优先研究的
股票”，并清楚回答：

- 数据是否真实、来自哪里、延迟多少、覆盖多少股票；
- 为什么这只股票排在前面，哪些因子贡献了分数；
- 适用哪种投资策略、持有期限和市场环境；
- 市场可能错在哪里，预期差如何被验证；
- 估值是否有安全边际，悲观情景损失多大；
- 哪些证据支持，哪些证据反对，缺少什么数据；
- 什么情况说明判断错误，何时重新研究；
- 如果进入组合，仓位、相关性、行业集中度和流动性是否合格；
- 历史与前向验证是否支持该策略，证据强度属于哪一级。

### 1.2 明确非目标

- 不承诺“每时每刻都找到未来涨幅第一的股票”。
- 不把模型置信度、技术评分、历史胜率解释成上涨概率。
- 不在休市或盘后把重复的收盘快照描述为“持续变化的实时行情”。
- 不以 LLM 记忆代替公告、财报、市场一致预期或行情源。
- 不为了高收益牺牲最大回撤、流动性、成交可实现性和证据质量。

## 4. P0：实时、真实、可用的数据底座

这是最高优先级。数据不满足要求时不运行高级策略。

### 4.1 两种实时等级

| 等级 | 用途 | 目标 | 说明 |
| --- | --- | --- | --- |
| 研究级免费源 | 当前默认 | 交易时段源时间延迟 P95 ≤ 10 秒；页面端到端 P95 ≤ 15 秒 | 最佳努力，不承诺交易所级 SLA |
| 专业行情模式 | 用户配置持牌/付费源后 | 源时间延迟 P95 ≤ 2 秒；端到端 P95 ≤ 5 秒 | 必须有授权数据源，不能靠免费接口伪造 |

如果当前数据源无法达到目标，页面必须显示实际 P50/P95、覆盖率和降级状态，不得显示
“实时”。盘后 `market_time` 不变化属于正常现象，前端应显示“收盘快照”。

### 4.2 行情链路改造

1. 自选股继续每 3 秒轮询并通过 WebSocket 推送。
2. 新建后台 `RealtimeRankingScheduler`，不要由浏览器请求触发重型全市场扫描。
3. 全市场扫描优先走 TDX 并行连接；若覆盖率已达到门槛，不得为少量 TDX 不支持代码
   阻塞等待慢速全市场回退。缺失标的单独异步补齐。
4. 日线特征只在数据库版本变化时重建；盘中只把最新行情合并到最后一根 K 线并增量计算。
5. 计算完成后写入内存中的不可变 `RankingSnapshot`，API 只读取最近快照，目标响应 <100ms。
6. 每个快照保存：`snapshot_id`、`source_time_min/max`、`received_at`、`generated_at`、
   `universe_size`、`quoted`、`fresh_quoted`、`coverage_ratio`、`compute_ms`、数据版本和策略版本。
7. WebSocket 新增排名通道；前端收到新 `snapshot_id` 才替换名单。
8. 上游失败时保留最近一次成功快照，但显式标记 `stale`、年龄和失败原因。超过安全上限后
   清空候选，不能无限沿用。

建议文件：

- 新建 `backend/app/realtime/ranking_scheduler.py`
- 新建 `backend/app/realtime/ranking_snapshot.py`
- 扩展 `backend/app/realtime/screener.py`
- 扩展 `backend/app/realtime/websocket_manager.py`
- 扩展 `backend/app/main.py`
- 扩展 `frontend/src/lib/ws.ts`
- 修改 `frontend/src/components/NowBuyPanel.tsx`

### 4.3 数据硬门禁

以下任意一项失败，`ranking_actionable=false`，候选列表为空：

- qfq 历史序列未覆盖到构造当日实时 K 线所需的前一交易日；
- 实时报价覆盖率低于 95%（北交所等明确不支持集合应单独报告，不混入分母）；
- 交易时段内报价 `source_time` 年龄超过配置阈值；
- 大面积价格、成交量、昨收或高低价自洽校验失败；
- 股票池快照过期、交易日历缺失或数据口径混用；
- 服务只能拿到缓存行情且缓存超过安全上限。

### 4.4 qfq 与 none 双口径维护

- qfq：用于跨除权窗口的收益、趋势和排名。
- none：用于真实价格、涨跌停、成交与执行模拟。
- 每日流水线分别报告两种口径的当日覆盖，不能用 qfq 完整推断 none 完整。
- 新上市股票不能因为不足 365 日被误判为数据失败；完整性从上市日或可用首日计算。
- 停牌日不能要求存在成交 K 线；交易日历完整性要结合标的交易状态。
- 对真正缺口设置定向重试队列，不要每天重跑全部 5,550 只一整年。

### 4.5 P0 验收

- 交易时段连续运行 60 分钟，记录端到端延迟分布、覆盖率和丢包；不能只测一次。
- 排名 API 热路径 P95 <100ms；后台全市场快照研究级 P95 ≤15 秒。
- 模拟 TDX 分片失败：接口立即返回带年龄的最后成功快照，后台重试，不出现 500。
- 模拟 qfq 缺少前一交易日：候选必须为空。
- UTC 12:55:42 必须显示为北京时间 20:55:42+08:00。
- 补数同时访问健康、首页、排名接口，不得出现 `database is locked`。

## 5. P1：专业级多策略投资引擎

不要继续在一个技术分数上无限加指标。先把收益来源不同的策略拆开，各自有股票池、期限、
退出规则和验证记录，再由组合层合成。

### 5.1 策略 A：质量价值（核心中长期）

适用：非金融、盈利模式稳定、财务数据足够的公司。建议期限 6–24 个月。

核心因子：

- 盈利质量：ROIC、ROE、毛利率/营业利润率稳定性；
- 现金兑现：经营现金流/净利润、自由现金流、应收和存货变化；
- 资本结构：净负债、利息覆盖、短债压力、商誉和稀释；
- 护城河代理：利润率稳定、资本回报持续性、研发效率、客户/供应商风险；
- 估值：FCFF/FCFE/股息模型适用性、EV/EBITDA、PE/PB 与自身历史/行业分位；
- 反向估值：当前价格隐含的增长率和利润率是否过度乐观；
- 安全边际：悲观情景价值与现价差，而非单一目标价。

硬门禁：财务公告时间未知、关键三表缺失、模型不适用、现金流持续不可解释、审计或退市
风险严重时，不给“高确信”标签。

### 5.2 策略 B：合理价格成长（GARP）

适用：盈利增长可持续且估值没有完全透支的公司。建议期限 3–18 个月。

关注：收入/利润/自由现金流增长的一致性、增量 ROIC、增长质量、行业空间、竞争格局、
估值对增长假设的敏感性。没有卖方一致预期时，`expectation_gap.available=false`；不得把
历史增速冒充市场预期。

### 5.3 策略 C：趋势质量（盘中/波段）

适用：流动性足够、趋势明确且基本面风险可控的股票。建议期限 5–60 个交易日。

因子：多周期动量、均线结构、突破质量、量价确认、ATR、波动收缩/扩张、相对行业和指数
强度。必须避免多个高度相关指标重复计分。退出包括趋势破坏、ATR 风险线、时间止损和市场
环境切换。该策略最接近当前实时雷达，应优先迁移现有逻辑并保留旧版本对照。

### 5.4 策略 D：周期反转

适用：盈利高度周期化且资产负债表能穿越周期的行业。建议期限 3–18 个月。

使用库存、价格、产能、资本开支、供需和估值分位；不得用周期底部低利润计算普通 PE 后
简单判定昂贵，也不得把商品价格单次反弹当作周期反转。没有周期数据时不启用。

### 5.5 策略 E：事件研究

适用：财报超预期、回购、重大合同、资产重组等有明确公告时间的事件。每类事件独立定义
样本、窗口、基准和交易规则。LLM 只能提取事件结构，最终事件时间和数值必须由代码校验。

### 5.6 市场环境识别

环境只使用当时可见信息，至少区分：趋势扩张、震荡、压力、流动性收缩。输入可包括宽基
趋势、市场宽度、成交额、涨停/炸板、横截面波动与相关性。环境用于调整策略权重和总风险，
不能事后按收益挑环境标签。

建议初始规则：

- 趋势扩张：提高趋势质量权重；
- 震荡：降低追涨，强调质量价值和均值回归；
- 压力：降低总仓位和单股风险，允许空仓；
- 流动性收缩：提高成交额门槛，降低组合容量。

### 5.7 横截面标准化和合成

每个因子先做行业内或全市场 winsorize，再转为分位数或稳健 z-score。方向、缺失值处理、
截面日期和版本必须固定。建议分层，而不是直接把所有原始数值相加：

```text
strategy_score =
    0.25 × quality
  + 0.20 × valuation
  + 0.15 × growth_quality
  + 0.20 × trend
  + 0.10 × catalyst
  + 0.10 × liquidity
  - risk_penalty
```

这只是待验证的起始假设，不是最终权重。每个策略使用自己的权重，市场环境层只在预注册
范围内调整。跨策略合成优先使用排名、证据等级和风险预算，避免不同量纲直接相加。

### 5.8 候选输出

每只候选必须输出：

- 策略名称、版本、期限和适用环境；
- 综合分及各因子贡献，不只给一个总分；
- 实时价格、源时间、数据年龄、行情来源；
- 估值区间、反向估值和关键假设；
- 支持证据、反方证据、缺失数据；
- 悲观/基准/乐观情景，不输出未经校准的概率；
- 失效条件、复核触发、观察指标；
- 流动性、波动、最大建议风险预算；
- 策略证据等级和最近验证日期。

## 6. P2：研究大脑与 DeepSeek 的正确职责

### 6.1 确定性计算与模型解释分离

代码负责：行情、财务、因子、估值、情景、组合约束、回测、门禁和所有数字。DeepSeek
负责：解释企业如何赚钱、形成可证伪论点、寻找反证、识别缺失资料、比较情景、生成复核
清单。模型不得改写代码给出的数字和门禁结果。

### 6.2 机构式研究流程

1. **事实整理**：只列证据包中的事实和口径。
2. **主论点**：说明收益驱动、预期差和传导路径。
3. **独立反方**：不看主论点结论，先从相同证据构造最强反例；每条必须绑定 evidence_id。
4. **综合审查**：逐条回答分歧，不能用模糊措辞跳过。
5. **决策门禁**：缺失关键数据、引用错误、数字越界、估值不适用、反方未回答时降级。
6. **冻结记录**：保存模型、提示词、证据、计算版本、成本、耗时和 SHA-256 指纹。
7. **复核**：按事件和时间触发新版本，不覆盖旧版本。

### 6.3 决策状态

仅允许：`insufficient_data`、`watch`、`research_candidate`、`paper_candidate`、
`reject`。在策略没有通过样本外与前向门禁前，不允许模型输出 `buy`、`strong_buy` 或
“必涨”。前端中文必须对应这些真实状态。

## 7. P3：严格验证体系

### 7.1 时间有效性

- 财务数据按实际公告时间进入信号，不按报告期提前使用。
- 股票池使用当时成员并包含退市样本，控制幸存者偏差。
- 收盘后生成的信号最早按下一交易日可成交价格模拟。
- qfq 用于收益与趋势，none 用于涨跌停和真实成交约束，禁止混用。

### 7.2 验证分层

| 等级 | 要求 | 可用标签 |
| --- | --- | --- |
| E0 假设 | 有逻辑和代码，无独立结果 | 未验证 |
| E1 历史探索 | 有训练期/探索结果 | 探索性 |
| E2 滚动样本外 | 多折 walk-forward，测试区间冻结 | 样本外观察 |
| E3 成本与压力 | 多成本、容量、延迟、参数扰动仍稳健 | 模拟候选 |
| E4 前向观察 | ≥60 个合格观察日，规则未变 | 前向观察通过 |
| E5 模拟盘 | 足够交易数和完整市场环境覆盖 | 可申请人工评审 |

任何阶段失败都保留。`production_ready_count=0` 时必须如实显示。

### 7.3 核心指标

同时报告：年化收益、基准超额、最大回撤、Calmar、Sharpe/Sortino、换手率、胜率、盈亏比、
样本数量、持仓集中度、行业暴露、容量、不同年份/牛熊/震荡阶段表现和置信区间。胜率不能
脱离盈亏比和样本量单独宣传。

### 7.4 反过拟合

- 预注册股票池、因子、方向、权重范围、持有期、成本和主评价指标；
- 嵌套 walk-forward：内层调参，外层只评估；
- 记录所有实验，不只保存最好结果；
- 参数扰动、起止日期扰动、成本翻倍、延迟成交、缺失数据压力测试；
- 多重检验修正和概率化 Sharpe/Deflated Sharpe 可作为研究项；
- 任何查看过的测试区间都不再称为完全未见样本。

## 8. P4：组合构建与风险控制

单股排名不等于组合决策。组合层至少实现：

- 总风险预算、单股上限、行业上限、主题共同风险上限；
- 波动率目标或风险平价作为起始方法；
- 60/120 日相关性与压力期相关性；
- 单笔损失预算、组合预期损失、最大回撤预警；
- 20 日成交额参与率、最小成交量和冲击成本；
- 调仓阈值和最小变动，防止频繁小额交易；
- 新候选必须与现有持仓比较边际贡献，不能只看自身分数；
- 风险环境恶化时允许降低总仓位或空仓。

止损分为：价格风险线、论点失效、数据失效和时间止损。模型只能解释，确定性代码决定
是否触发。组合草案保持只读；执行继续走模拟盘人工确认。

## 9. P5：前端产品重构

首页第一屏按以下顺序展示：

1. 市场状态：交易时段、行情源、源时间、端到端延迟、覆盖率、是否降级；
2. 最新排名快照：快照时间、策略版本、数据版本、后台是否重算；
3. 前五研究候选：策略、综合分、因子贡献、证据等级、风险和失效条件；
4. 组合风险摘要；
5. 数据/策略异常和待复核事项。

交互规则：

- “！”图标悬停必须解释指标定义、数据来源、更新时间、门禁和限制；
- 缓存结果显示年龄，不用当前时钟替代原生成时间；
- 盘后明确显示“收盘快照，输入未变化时排名不会变化”；
- 候选变化显示新进、退出、名次变化及主要因子变化；
- 不显示无法解释的总分；点击可展开贡献和证据；
- 证据未通过时用“研究候选”，不得用“推荐买入”；
- 手机和桌面均可读，关键告警不能只靠颜色表达。

## 10. P6：性能、数据库和运维

### 10.1 性能

- 保持 SQLite WAL；记录 checkpoint、WAL 大小和长事务。
- 用查询计划确认日线、快照、研究记录的索引；禁止无依据增加索引。
- 日线特征按数据版本缓存；实时计算采用数组化或增量方式。
- 后台任务限并发、可取消、可恢复；不得一次创建 5,550 个无界任务。
- API 记录 P50/P95/P99、错误率、缓存命中和后台刷新耗时。

### 10.2 数据流水线

- 交易日收盘后依次：交易日历 → 股票池 → qfq/none 增量 → 财务/情绪 → 排名快照 →
  选股冻结 → 模拟盘结算 → 完整性报告。
- 每一步有状态、进度、重试、错误分类和幂等键。
- `partial` 必须区分新股历史不足、停牌、源缺失和真实断档。
- 定向重试失败标的；达到覆盖阈值可以继续研究，但缺失标的不得进入候选。

### 10.3 备份

- 备份前做磁盘空间检查；使用 SQLite 在线备份或安全 checkpoint。
- 保留最近完整备份并定期验证 restore；半截备份自动标记失败。
- 每次迁移前生成一致性备份，报告 SHA-256、integrity、外键和表数。

## 11. P7：安全、发布与商业化

- GitHub 公开仓库不得包含数据库、WAL/SHM、`.env`、密钥、用户研究记录和日志。
- 提供 `.env.example`，所有密钥通过本地环境配置。
- 默认仅监听本机；LAN/公网必须启用鉴权、限流和审计。
- 0.5 美元付费不能只靠 GitHub 公共源码限制使用。公开源码与付费服务要明确区分：
  可选择赞助、托管服务、数据服务或高级模型额度，但必须遵守数据源许可。
- README 说明安装、启动、数据下载、功能、限制、证据等级、隐私和风险。
- 发布 Release 时提供源码包校验值、迁移说明和升级/回滚步骤。

## 12. 分阶段实施顺序

### R0：基线冻结与故障复现

输出当前 Git HEAD、数据库模式、数据覆盖、API 延迟、行情年龄、排名结果、全量测试和备份。
复现已知故障，建立基准报告。不得改代码后再补写“改前数据”。

### R1：实时排名数据面

完成后台快照、TDX 快速路径、覆盖率门禁、WebSocket 排名推送、缓存/失败降级和盘后语义。

### R2：双口径日线与增量流水线

完成 qfq/none 每日增量、定向重试、上市/停牌完整性规则和数据质量面板。

### R3：多策略框架

先实现质量价值、GARP、趋势质量三种；周期与事件数据不足时保持 disabled，并说明依赖。
所有策略有独立版本、配置、适用环境和因子贡献。

### R4：市场环境与组合层

实现环境识别、策略权重、去相关、容量、行业和风险预算；只生成模拟草案。

### R5：证据研究闭环

把策略候选接入冻结证据包、主审/反方、失效条件、自动复核和组合草案。

### R6：严格验证

完成预注册、嵌套 walk-forward、压力测试、前向观察和证据等级。不能因结果不好跳过。

### R7：前端与可观测性

完成首页、变化归因、悬停说明、延迟图、策略证据页、任务状态和错误恢复体验。

### R8：发布

全量测试、真实运行检查、恢复测试、文档、Release、GitHub 更新。实盘仍保持关闭。

1. 代码路径和功能入口明确。
2. 正常、缺数据、过期、上游失败、部分覆盖、服务重启均有测试。
3. 所有时间带时区，所有数字带单位和口径。

7. 数据库变更有迁移、备份和恢复验证。
8. README、功能报告和阶段报告同步更新。
9. Git diff 无密钥、数据库、大文件和临时脚本。
10. 独立提交并推送 GitHub，报告 commit hash；工作区干净。

## 15. DeepSeek 首次执行任务

收到本方案后，先执行 R0 和 R1，不要同时大改全部模块：

1. 检查 Git 状态，阅读最近 10 个提交，保护其它会话的未提交修改。
2. 只读核验 qfq/none 最近交易日覆盖、股票池、交易日历和 WAL。
3. 在交易时段分别连续测量 TDX 单股、自选股、全市场排名 60 次；盘后只做功能验证，
   不把收盘快照的重复返回当作实时变化。
4. 画出从数据源到首页的延迟分解，指出真正瓶颈。
5. 实现后台 `RankingSnapshot` 与调度器，先让 API 热路径 <100ms。
6. 实现 TDX 覆盖达标后的快速返回；剩余缺失标的异步补齐。
7. 增加数据新鲜度、快照年龄、刷新错误和硬门禁测试。
8. 前端显示“本轮实算/最近成功快照/后台重算/收盘快照”，并提供“！”详细说明。
9. 提交阶段报告 `docs/阶段报告-R1-实时排名数据面.md`。
10. R1 经实测通过后，再进入 R2；不要提前宣称顶级策略完成。

R3 开始时，先提交 `docs/顶级多策略-预注册设计.md`，把质量价值、GARP、趋势质量的
收益机制、因子、方向、股票池、持有期、退出、成本、基准、参数范围和失败标准全部冻结，
再写策略代码。只有达到 E2 以上的策略才能进入模拟候选，达到 E4/E5 并经人工评审后才能
讨论生产使用。

## 16. 最终完成定义

只有同时满足以下条件，才可报告“完整优化完成”：

- 实时数据链路达到选择的 SLA，延迟和覆盖可见，故障会安全降级；
- 排名 API 快速稳定，后台快照持续更新，盘后语义正确；
- qfq/none、财务、股票池和公告时间口径可追溯；
- 至少三类策略独立实现且有因子贡献、环境和失效条件；
- 候选、研究证据、反方审查、组合风险、模拟盘和复盘形成闭环；
- 严格样本外、成本压力和前向观察结果完整展示，包括负结果；
- 前端所有原功能保留，关键指标有悬停说明；
- 全量测试、真实端到端、数据库一致性、备份恢复、GitHub 文档全部通过；
- 没有把任何未经验证策略称为“顶级收益策略”或“最优股票保证”。

如果策略最终没有通过验证，正确结论是“系统工程完成，策略证据未通过”，而不是继续调参
直到得到好看的回测。
